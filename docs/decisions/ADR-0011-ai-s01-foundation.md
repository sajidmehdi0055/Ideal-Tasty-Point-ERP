# ADR-0011: AI-S01 — AI Foundation (Gateway, Providers, Read-only ERP Tools, Audit)

Date: 2026-09-27
Status: **APPROVED — owner decisions 2026-09-27** (answered in the Cowork Manager session for AI-S01; technical design by the Manager within those decisions)
Scope: Cross-cutting AI layer. Makes the ERP structurally AI-ready without changing any existing business rule, API contract or table. Phase 1 only.

## Owner decisions (2026-09-27)

- **AI-O-01 — Phase 1 is read-only.** AI-S01 delivers the AI gateway, provider abstraction, read-only ERP tools over the existing Inventory/Purchasing services, permission enforcement and an AI audit log. The write-action approval flow is only a response contract and interface in this slice; the first write tool (AI-proposed Purchase Order draft → preview → approve → existing `PurchaseOrderService`) is deferred to AI-S02.
- **AI-O-02 — Cloud providers are built but OFF by default.** OpenAI-compatible and Anthropic providers exist in code, but no ERP data may be sent to any cloud provider unless the owner sets `AI_CLOUD_ENABLED=true`. The whole AI layer is also OFF by default (`AI_ENABLED=false`).

## Technical decisions

- **D-01 Layering.** `/api/ai/*` route → `AiGateway` (orchestration, limits, audit) → `AiProvider` (primary, optional fallback) and `AiToolRegistry` → existing application services → existing repositories → PostgreSQL. The model never gets SQL, shell or file access; it can only request registered tools.
- **D-02 No new dependency.** Providers use Node 24's built-in `fetch`. One `openai-compatible` adapter serves both the local model (any server exposing `/v1/chat/completions`, e.g. Ollama, LM Studio, llama.cpp server, vLLM) and OpenAI; one `anthropic` adapter speaks the Messages API. `fetch` is injectable so tests never call a network or paid API.
- **D-03 Local-first, cloud gated.** `AI_PRIMARY_PROVIDER` defaults to `local`. `openai`/`anthropic` are "cloud" providers: configuring one as primary or fallback while `AI_CLOUD_ENABLED` is false is a configuration error (AI reports `MISCONFIGURED`; the ERP keeps running). With cloud disabled, the `local` base URL must also be on-premises (loopback, private/LAN address, single-label or `.local`/`.lan` host name); otherwise it is `MISCONFIGURED` too. The fallback is tried for any model call of a request whose primary call fails with a retryable error (network error, timeout, HTTP 429/5xx, malformed response); a call that succeeded is never repeated, and once the fallback is used the rest of that request stays on it. Automatic complexity-based routing is deferred.
- **D-04 No second permission system.** Each tool declares an `authorize(auth)` function that reuses the existing guard (`requireItemEditor` → OWNER/MANAGER for all Phase 1 tools). Only tools the caller is authorized for are shown to the model; every requested call is re-checked server-side, and the underlying service performs its normal guard and branch scoping with the caller's own `AuthContext` (defence in depth). Model or client input never supplies identity or permissions.
- **D-05 READ vs WRITE.** Tools carry `mode: 'READ' | 'WRITE'`. READ tools run automatically after authorization and zod validation. WRITE tools are never executed by the gateway: they may only return a `proposed_action` (with `requires_approval: true`), and only when `AI_WRITE_ACTIONS_ENABLED=true`. No WRITE tool is registered in AI-S01.
- **D-06 Deterministic numbers.** Tools return service results unchanged (NUMERIC values stay decimal strings). The tool layer only filters/limits lists for the model (name search, `limit`); it performs no business calculation. The system prompt forbids inventing or recalculating ERP figures.
- **D-07 Audit.** New append-only table `ai_audit_log` (one `CHAT` row per request — including requests refused with 403 `DENIED` or 429 `RATE_LIMITED` — and one `TOOL_CALL` row per acknowledged tool call, including denied/invalid/unknown ones and calls over the per-round limit (`TOOL_CALL_LIMIT`, not executed); a model turn with more than 32 tool calls has the excess dropped and counted in the CHAT row's `details.dropped_tool_calls`): actor, role, branch, request id, optional conversation id, provider, model, prompt version, tool name/mode, sanitized parameters (validated arguments only, strings truncated, control characters such as NUL removed), permission result, approval status, outcome, error code, duration. The user's message text and model answers are **not** stored. Rows are immutable (UPDATE/DELETE/TRUNCATE rejected by triggers even for the schema owner). The runtime role gets INSERT only (no SELECT). Audit is fail-closed: if a row cannot be written the request fails with `500 AI_AUDIT_FAILED` and no answer is returned.
- **D-08 Stateless conversations.** No `ai_conversations`/`ai_messages` tables. The client sends recent history (text only, `user`/`assistant` roles, bounded); tool and system messages from the client are rejected. A client can put invented assistant turns in its own history; this affects only that user's own answer (it cannot add tools, change permissions or reach the system prompt). Persisted conversations can be added later without changing the gateway contract.
- **D-09 Limits and safety.** Request timeout per provider call, max model calls per request (`AI_MAX_TOOL_ROUNDS`, counting the final answer), max executed tool calls per round, max tool calls per round, max tool result size, per-user in-memory rate limit, message and history size limits. Tool results are passed to the model as data wrapped with a note that they are not instructions (prompt-injection mitigation). Provider error bodies and secrets are never returned or logged.
- **D-10 System prompt.** One central, versioned prompt (`src/ai/system-prompt.ts`, version `erp-ai-v1`). Replies follow the user's language (Roman Urdu / Urdu / English).
- **D-11 APIs.** `GET /api/ai/status` (authenticated; state `DISABLED`/`READY`/`MISCONFIGURED`; provider/model names and flags only for users who may use the assistant (`available`), never keys; `?check=true` runs a provider health check with the same role gate and rate limit as chat) and `POST /api/ai/chat` (authenticated; structured response `{ message, provider, model, tool_calls[], requires_approval, proposed_action, metadata }`). When AI is disabled or misconfigured both still answer (`503 AI_DISABLED` / `503 AI_UNAVAILABLE` for chat); no other route is affected.
- **D-12 Knowledge/RAG extension point.** A `KnowledgeProvider` interface (with a no-op default) is defined but not wired to a tool until SOP/policy documents exist.

## Phase 1 tools (all READ, OWNER/MANAGER, branch-scoped via the existing services)

`inventory_list_stock_locations`, `inventory_get_stock_balances`, `inventory_get_stock_movements`, `inventory_list_suppliers`, `inventory_list_pack_variants`, `inventory_compare_purchase_rates`, `inventory_get_purchase_history`, `inventory_list_purchase_orders`, `inventory_get_purchase_order`, `inventory_list_goods_receipts`.

Not possible yet (would require inventing business rules or data that do not exist): low-stock alerts (no reorder level), days-of-stock / consumption rate (no consumption/issue movements), sales, POS, cash, wastage, HR/attendance.

## Consequences

- Existing endpoints, tables, grants and tests are unchanged; the migration is additive. After applying it, re-run `scripts/runtime-grants.sql` (existing upgrade order).
- Rate limiting is per API process (in-memory); a multi-process deployment needs a shared limiter later.
- Real authentication is still missing (ADR-0006 boundary); the AI endpoints are protected by the same `AuthContextProvider` as every other route, so the standalone server denies them exactly like the rest of the API.
